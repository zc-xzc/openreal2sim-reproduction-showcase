# 故障案例与排查方法

[返回总览](../README.md)

本页保留通用排查方法，描述的是需要防范的故障模式，不构成特定个人项目的实验记录，也不应作为自动修复指令。具体包名、版本、动态库路径和权限应以目标环境为准。

## Python 依赖与版本兼容

**可能现象：** 模块找不到；SAM2 依赖缺失；ONNX 导入过程中出现 protobuf descriptor 错误；Gradio 提示 `css` 参数迁移。

**排查顺序：** 先确认正在用哪个 Python 与环境，再核对模块来源、版本、依赖约束和完整异常链。把模块缺失、版本不兼容、导入时触发的下游错误分开。安装名称不一定与 import 名称相同。

**处理边界：** 可考虑核对依赖、protobuf兼容设置与Gradio接口。没有完整依赖锁定文件，不能将这些零散版本拼成已验证的 requirements。也不能把某次启动成功推断为整套依赖完全兼容。

## 无头图形运行时与 pymeshlab 崩溃

**可能现象：** Open3D 缺少 `libEGL.so.1`；pymeshlab 导入时发生段错误。

**排查顺序：** 在独立最小进程中复现导入，检查动态库加载与图形后端，不要把 Python 包已经安装视为系统库齐全。GPU 可见与 EGL/GL 能加载是两项检查。

**处理边界：** 可能需要补齐图形运行时；不要直接用trimesh替代pymeshlab并宣称等价。替代模块的源码和测试缺失，不能判定 API 或数值等价。段错误的确切根因也不能仅由“无头环境”四字证明。

## CUDA 扩展能编译却不能加载

**可能现象：** Hunyuan3D 扩展与 Torch 动态库的查找路径需要适配。

**排查顺序：** 核对 Python、Torch、CUDA 工具链、驱动和目标 GPU 架构，区分构建失败、找不到模块、找不到共享库和 ABI 不匹配。构建成功后还应在目标运行环境导入并做最小计算。

**限制：** 某个容器中的绝对路径或 `LD_PRELOAD` 不是跨环境解法。保存二进制扩展后，基础镜像或 Torch 变化仍可能使其失效。

## ICP 运行很慢

**可能现象：** 场景组装处理大量点时耗时过长，随后使用 `fast_scene_construction=True`。

**归属：** 这是上游已有选项的使用，不是本案例发明的算法。

**验证要求：** 固定输入、硬件、版本和随机种子，比较默认与 fast 配置的多次运行时间，同时检查几何配准误差、失败率和下游质量。本候选没有受控数据证明加速比或精度不变。

## FoundationPose 缺失导致下游字段不全

**可能现象：** `pytorch3d` 不可用，FoundationPose 被跳过，下游仍期待 `fdpose` 或 trajectory。

**处理边界：** 使用 `registered` 配准结果继续部分后处理，并让 trajectory 缺失不阻断导出。

**风险：** 这是流程语义变化。ICP 位姿未经 FoundationPose 精修；未运行的阶段不能报告通过。宽泛捕获 `ImportError` 还可能掩盖阶段内部缺陷。最终补丁需要验证“依赖缺失”和“已有依赖但运行失败”两类情况，不把所有错误自动跳过。

缺失字段的测试至少覆盖：只有 `fdpose`、只有 `registered`、二者都有、二者都没有、trajectory 缺失。不能直接照抄 `dict.get` 默认参数内的字典索引，默认表达式会先求值。

## 日志没有更新

**可能现象：** 后台运行的标准输出存在缓冲，看起来像任务卡住。

**排查顺序：** 结合进程、退出状态、资源使用和输出更新时间判断，不仅看日志是否增长。无缓冲输出便于观察，但不会修复计算故障，也不能单凭出现新日志判定任务正确。

用管道保存日志时要保留实际验证进程的退出码，避免只检查日志工具的退出状态。

## 冷启动检查出现假通过

**可能现象：** Python 导入区块打印错误，却未影响 shell 的 FAIL 计数。应检查每项失败是否影响最终退出码。

**验证要求：** 人为注入一个可控失败，确认检查项、汇总计数和退出码都失败；验证超时、子进程失败和日志写入异常。此处提出的是后续测试方案，本仓库尚未执行这些故障注入测试。

固定检查脚本版本、检查项定义和实际日志。摘要中写了 `PASS` 或一个 SHA256 字符串，本身都不能证明被测系统通过。

## 新容器目录为空

**可能现象：** 空子挂载遮住共享存储中的内容，表面上像数据丢失。

**排查顺序：** 先检查挂载来源、目标、类型、父子覆盖与目录权限。持久卷标记文件在多个容器中相同，不足以识别哪一个容器的系统层安装完整。

在确认前不要删除空目录、覆盖恢复、移动大文件或直接卸载。修复方式取决于平台，不应套用未核实的界面操作。

## 带有 No space left 的警告

inotify警告不一定是服务退出原因。排查时要区分磁盘容量、inode、监视器数量限制和实际导致退出的异常。不能因为这一行就清空临时目录，也不能永久忽略它在另一次运行中的影响。
