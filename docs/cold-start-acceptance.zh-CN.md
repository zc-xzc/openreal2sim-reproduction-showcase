# 冷启动验收协议

[返回首页](../README.md) · [工程案例](archive-engineering-case.zh-CN.md)

本协议是根据历史检查器问题重新整理的建议，未在GPU环境实际执行。它不包含旧服务器的恢复脚本或私人配置。

## 分开四种结果

1. 当前环境自检：依赖与核心最小计算能否通过。
2. 旧产物可读：已有文件结构与引用是否有效。
3. 真冷启动：新镜像/新容器，不预先修补，能否通过相同检查。
4. 新输入复跑：使用合法固定新输入，重新预处理、标注、重建并验收。

每项单独记录。先修复再检查可称修复后验证，但不能伪装成原镜像直接通过。读取旧场景不是重新生成场景。

## 检查器本身的要求

- 以真实退出码为主要机器判据，诊断文字不参与PASS字符串等值比较。
- 必需项非零退出、超时、信号终止或解析失败必须计失败。可选项按事先定义的范围单独记录。
- 不只grep某种ERR前缀。异常traceback、解释器崩溃和动态库故障可能使用不同输出。
- 保存stdout、stderr、超时与退出原因；日志管道须保留被测进程的状态。
- 最终结果任一必需项失败即失败；未运行和跳过不计通过。
- 运行前校验脚本内容非空、编码、语法和hash；语法通过不能证明逻辑正确。

## 最小故障注入清单

在一次性隔离测试环境分别模拟缺模块、普通非零退出、超时、空输出、包含PASS字样的失败输出，以及包含警告的成功输出。确认计数、阶段状态和最终退出码一致。不能为做测试破坏已有环境或系统设置。

## 环境与输入身份

分别记录源码/子模块/补丁、镜像digest、系统包、Python解析结果、Torch/CUDA/驱动、编译扩展、模型revision/hash、挂载来源与配置。只收集所需字段，不记录认证信息。

人工完成标注保存与重载；逐阶段记录completed/skipped/failed/not_run。FoundationPose缺失时应停止完整验收，或另立明确降级案例，不把结果并入完整成功率。

使用 [冷启动记录模板](../templates/cold-start-record.json)。模板全为空，不是本次实验结果。
